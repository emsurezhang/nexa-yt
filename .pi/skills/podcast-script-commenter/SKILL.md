# Script Commenter：脚本点评

给一份脚本做一次"编辑级"的审读：先告诉作者哪里最危险，再告诉他哪里可以更好，每条建议都能直接照着改。

## 为什么要这样做

作者拿脚本来问"有什么建议"，通常是想在发布或配音前做最后一道把关。尤其是 AI Agent 生成的脚本，最常见的问题不是文笔，而是：具体人名、数字、引语可能是编的；标题和正文互相打架；写给眼睛看的句子放进 TTS 会读错。所以点评要**先抓风险，再谈打磨**，不要一上来就夸文笔或堆砌泛泛的写作建议。

## 工作流程

### 1. 读懂脚本，不要先问问题

完整读一遍，默默判断：

- **形式**：单人口播 / 双人对话 / 多人访谈 / 视频分镜？
- **用途**：发布到哪里？是否要交给 TTS？（看有没有情绪标签、"供 TTS 配音"之类的字样）
- **来源**：是否像 AI 生成的？（大量具体引用、整齐的段落结构、套路化接话）
- **主线**：一句话概括这期想讲什么、想让听众带走什么

这些信息大多能从脚本本身推断，直接推断，不要用问题打断用户。只有当形式或用途真的无法判断、且会明显影响建议时，才问一个问题。

### 2. 按优先级逐层检查

按下面的顺序检查，**风险大的放前面**。每一层的详细检查项见 `references/checklist.md`，需要时再读。

1. **事实与引语核查**：人名、头衔、公司、日期、数字、"原话"、出处是否可疑或需要核实
2. **前后自洽**：标题承诺 vs 正文兑现；开头的说法 vs 后面的解释；相互矛盾的论点
3. **措辞与表述**：标题党、暗含错误因果的说法、会过期的相对时间、概念混用
4. **内容结构**：有没有具体案例、有没有兑现标题、有没有反面视角、结尾行动号召是否聚焦
5. **对话节奏**（仅多人脚本）：谁在主导、是否只是"递话"、口头禅是否重复、情绪标签是否套路化
6. **TTS 适配**（仅用于配音的脚本）：外文名/缩写、数字符号、情绪标签支持度、长句换气

不适用的层直接跳过，不要为了凑齐结构硬写。

### 3. 事实核查的处理方式

- 默认**只标出"需要核实"的点并说明为什么可疑**，不要声称某条"错了"或"对了"，除非你真的查证过。
- 用户要求核实，或有搜索工具且用户明确同意时，再逐条搜索，并在结果里区分：已证实 / 未找到出处 / 与来源不符。
- 对"原话"类引语特别谨慎：翻译过的引语建议改成"大意是"，或附英文原句。

### 4. 输出格式

按下面的结构组织，用中文小标题分层，用户的脚本是什么语言就用什么语言回复：

```
（开头 1–2 句）整体评价：脚本做得好的地方 + 最需要优先处理的一件事

## 一、先核实事实（最重要）
- 逐条列出需要核对的点，说明为什么

## 二、措辞上的小问题
1. **问题概括**：位置/原句 → 为什么有问题 → 建议怎么改（给出改后的示例）

## 三、内容结构
……

## 四、对话节奏（如适用）
……

## 五、TTS 适配（如适用）
……

（结尾）一句话给出下一步选项，例如：先做事实核查，还是直接给一版修改稿
```

写法要点：

- **每条建议 = 定位 + 原因 + 改法**。"节奏偏慢"这种诊断没有用，"第三段小硕连续 200 字独白，建议拆成两段，中间让小丽插一句质疑"才有用。
- **引用具体位置**：写出章节名或原句的关键词，让作者一眼找到。
- **解释"为什么"**：让作者理解问题，而不是只会机械照改，这样他下次自己也能避开。
- **控制数量**：每层最多 3–5 条，只保留真正值得改的。一份 30 条建议的清单等于没有建议。
- **语气**：像一位靠谱的同行编辑，直接但友善。先肯定确实做得好的地方，但不要套话式夸奖。
- **不要擅自重写全文**。用户只问建议时，提供局部改法示例即可；用户明确要修改稿再整体重写。

### 5. 收尾

结尾只给一个清晰的下一步（例如"要不要我先逐条核实事实，再给你一版修改稿？"），不要罗列一堆选项。

## 关键原则速记

- 风险优先：事实、引语、自洽问题排在文笔前面
- 具体优先：每条建议都能直接执行
- 按需检查：形式不适用的层直接跳过
- 诚实标注：没查证就说"需要核实"，不说"这是错的"
- 克制篇幅：宁可少而准，不要多而杂
