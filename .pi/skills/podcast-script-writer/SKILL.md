# 1. 何时使用
用户或Agent提供了一份选题 / 调研 结果的JSON文件，并要求生成播客脚本、对话稿、双人播客文案。
用户说"把这些素材/笔记做成播客""写一期播客节目""生成两个主播的脚本"等。
不要求用户必须给出严格 schema——只要输入本质上是"一个主题 + 多条带证据的观点"，都可以套用本流程；缺失字段就跳过对应环节，不要报错卡住。

# 2. 输入约定

期望输入是类似如下结构的 JSON（字段名可能略有出入，需灵活适配）：

topic: { title, description }
materials: [
  {
    video_title / source_title,
    channel / source,
    relevance_level,           # 高相关 / 待定通过 等，用于决定该素材权重
    core_viewpoints: [
      { claim_quote, evidence: [...] }
    ]
  },
  ...
]
excluded_candidates: [...]     # 通常不进脚本，除非用户要求提及"我们筛掉了哪些"

# 3. 处理原则：

relevance_level 为「高相关」的素材是主体内容，应覆盖其大部分 core_viewpoints。
「待定通过」或权重较低的素材，挑 1 个最有价值的点带过即可，不必逐条展开。
evidence 里的英文原文引用（claim_quote / evidence 字段）不能逐字照搬照读——把内容转述为主播口语化的中文表达，可以保留关键术语（如 "FDE"、"Echo team"、"gravel road → paved highway"）但要重新组织成自己的话，避免大段"翻译腔"直译。这既是版权要求，也是播客可信度要求（真实主播不会照着 PPT 念）。
alternative_candidates（备选选题角度）可以在开场或结尾作为"如果你对哪个角度更感兴趣，欢迎留言"式的引导，不必展开讲。
工作流程

## 3.1 第一步：通读素材，规划节目结构

在动笔前，先在心里（或简短笔记里）梳理：

核心叙事线：这期播客要按什么逻辑推进？常见结构：
时间线 / 起源型：从概念起源讲到现状演变（例如本例：Palantir 起源 → 方法论拆解 → 边界辨析 → 未来演变）
问题拆解型：先抛出一个反直觉观点，再逐层拆解证据
对比辩论型：两种视角交锋（例如"FDE 到底是不是伪概念"——Natalie Meurer 的"dirty secret"观点可以和其他材料形成张力）
分段（segments）：把 topic.description 里提到的几个讨论点，转成 4-7 个自然段落节点，每段对应 1-2 条 material 的核心观点。不要简单按 material 顺序罗列，而要按逻辑重新编排、交叉引用（比如把 a16z 素材里的 "backprop" 比喻和 Palantir 起源素材放在一起讲）。
张力点/爆点：找出素材里最反直觉或最有梗的说法（例如 "dirty secret: FDE doesn't exist"、"pain is a moat"、"FDE = dev shop 陷阱"），作为对话的转折或主播互相抬杠的切入点。
收尾走向：呼应 alternative_candidates 或 topic 里提出的开放问题，给听众留一个思考点。

## 3.2 第二步：设定两位主播人设

除非用户指定了名字/人设，默认使用：

主播 A（"小硕"）：主阐述位。承担绝大部分内容输出——背景信息、观点展开、数据与例子落地、结构性总结，语气稳健、爱打比方。字数约占全篇 80%–85%。
主播 B（"小丽"）：提问与衔接位。负责发问推进（"具体怎么做到的？""那代价是什么？"）、段与段之间的承上启下、适时质疑或从产品/从业者视角补刀，语气更活泼、爱举反例。字数约占 15%–20%，但每句都要承担结构功能：段首的问题引入、段间的过渡小结、关键处的反驳抬杠——不是凑数的陪衬。

两人分工感：小硕负责"展开讲清楚"，小丽负责"问出听众想问的、并把节目串起来"。避免两人观点/语气雷同，也避免机械问答体——小丽的提问要短而准，小硕的阐述要有起伏、有细节，不是小丽问一句小硕答一句的交替打卡。

## 3.3 第三步：撰写脚本正文

格式：

【开场】
**小硕**：...
**小丽**：...

【第一段：XXX】
**小硕**：...
**小丽**：...
...

【第二段：XXX】
...

【结尾】
**小硕**：...
**小丽**：...

# 4. 语言与风格要求：
- 全程使用口语化中文（除非用户要求其他语言），可以保留必要的英文术语（FDE、PM、outcome-based pricing 等），但解释要用中文讲清楚。
- 句子偏短，多用"对对对""你这么一说我想起""等一下我插一句"之类真实对话连接词，但不要过度堆砌到显得油腻，每隔几句穿插一次即可。
- 每个观点落地前，先有一句"人话版"总结，再补一两个具体例子/数据（如 Palantir ACV 400万、30000个岗位空缺等具体数字，这类事实性数字可以保留原样引用，因为这是事实而非受版权保护的表达）。
- 主播之间要有真实互动：追问"具体怎么做到的?"、复述对方观点再补充、适度反驳（"我觉得这个说法有点绝对啊……"）、类比日常经验。
- 避免逐条"材料1怎么说、材料2怎么说"的报菜名体;要把多个 material 的观点揉在同一段对话里自然过渡，像是主播读过全部材料后聊出来的,而不是照着提纲念。
- 节目时长默认为 5 分钟：中文口播语速约 4-5 字/秒，脚本正文中文字数约 1200-1500 字（不含语气标签与章节标注）。用户指定其它时长时按同比例换算（时长 × 60 秒 × 4.5 字/秒）；无论时长多少，优先保住高相关素材的核心论点，不要为了凑数硬灌水，也不要因为省字而漏掉反直觉观点。
- 结尾给出一个开放式问题或行动号召（例如"如果你也在带 FDE 团队，欢迎告诉我们你们是怎么定义 echo/delta 分工的"），不要用"感谢收听，我们下期再见"这种空洞收尾——可以有，但前面要加一句有内容的总结。
- 引用素材时，说明来源（谁在哪个节目上（title），什么时间发表/播出），并尽量用口语化的方式告诉听众。不要出现“素材里说”。

# 5. 语气标签（Tone Tags）

为了让生成的脚本可直接用于 TTS 配音，撰写脚本时要在文本中插入语气标签。标签直接插入在人类说话者自然会发出该声音的位置——不要无谓地加标签，只在确实能提升自然度、且符合说话者情绪状态和上下文的位置插入。

## 5.1 可用标签

1. 笑声与叹气
- [laughing] — 插入在幽默、轻松内容之前或之中
- [sigh] — 插入在疲惫、无奈或情绪化的内容之前或之中
2. 停顿与思考
- [Uhm] — 短暂的犹豫、思考或口头填充
- [Shh] — 让人安静或压低声音的嘘声
4. 情绪
- [Surprise-wa] — 惊讶反应，"wa" 感叹
- [Surprise-yo] — 惊讶反应，"yo" 感叹
- [Dissatisfaction-hnn] — 不满、不悦或抱怨的声音

## 5.2 使用规则
- 始终使用英文标签形式加方括号，严格照写（小写，括号内无空格）。
- 标签放在应发出该非语言声音的位置，通常放在相关词语/短语之前。
- 保持原文本不变——标签是插入，绝不替换或删除原文。唯一例外见下一条。
- 【去重铁律】部分标签本身会"发声"：[Surprise-wa] 会发出"wa"音、[Surprise-yo] 会发出"yo"音、[Dissatisfaction-hnn] 会发出"hnn"音。插入这类标签时，必须删掉正文中紧邻的同义字面感叹词（哇 / 哟 / 哼 / 嗯哼等），否则 TTS 会重复发声（先标签的"wa"再念一个"哇"）。例如 `[Surprise-wa] 这数据也太夸张了吧` ✅，`[Surprise-wa] 哇，这数据也太夸张了吧` ❌。
- 标签要省着用：每段短对话通常 1–3 个就够了；过度使用会显得不自然。
- 标签服务于主播人设：小硕的标签偏稳健（偶尔的 [Uhm] 思考感），小丽的标签偏活泼（[laughing]、[Surprise-wa]、[Question-ei] 等），与第 3.2 节的人设分工一致。

# 6. 自查清单

写完后过一遍：
- 字数是否落在目标时长档位（默认 5 分钟 ≈ 1200–1500 字）？
- 小硕/小丽字数比例是否约 8:2，且小丽承担了发问、承上启下与反驳的结构功能，而非机械陪衬？
- 语气标签是否与字面感叹词去重（无 `[Surprise-wa] 哇` 这类叠用）？
- 是否覆盖了所有「高相关」素材的关键 core_viewpoints？有没有漏掉重要反直觉观点？
- 引用是否都转述成了口语化表达，而不是逐字翻译原始英文引文？（数字、专有名词、机构名可以照抄，句子表达不能照抄）
- 两位主播是否各有语气特点，不是同一个人在自问自答？
- 是否有真实的"追问-反驳-举例"互动，而非单向输出？
- 结构是否有清晰的段落推进（不是素材的简单罗列）？
- 开头是否用一个钩子/反直觉说法迅速抓住听众，而不是"大家好，今天我们聊聊FDE"这种平淡开场？
- 结尾是否有实质总结或开放问题？
- 语气标签是否按第 5 节的规范适度使用（每段短对话 1–3 个、位置恰当、符合主播情绪）？是否保持了原文本不被替换或删除？

# 7. 输出方式

主脚本与 summary 是两个文件，都保存在当前项目目录中：

1. 主脚本：`podcast-script-<topic关键词>.md`（含语气标签，直接供 podcast_tts 配音）。
2. 节目简介：`podcast-summary-<topic关键词>.md`，用于发布到播客平台时向听众介绍内容、吸引点击。要求：
   - 节目标题 + 可选副标题（突出冲突点或反直觉点，不要平淡的"第X期：聊聊XX"）；
   - 一句话钩子（≤30 字，点出本期最抓人的问题或结论）；
   - 节目简介 100–200 字：面向潜在听众写清"这期讲什么、为什么值得听、听完能获得什么"，口语化、有信息量，可含关键数字；
   - 3–5 条本期看点（每条一行，短句）；
   - 结尾附一句互动引导（提问或征集听众经验），与主脚本结尾的开放问题呼应；
   - 全文不出现语气标签，不要"主播A/主播B"等内部称谓。
